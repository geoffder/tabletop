# Logic

- Model a move the player makes in several clicks as several Actions with machine states between them (place, then remove; each jump of a chain; push, then take a row). Undo then steps back one click at a time, and history can group them.
- **Give every piece a stable id in State from the first commit.** Specks, history jumps, another player's Undo and lean metadata all rest on it, and the review rewrote every title that lacked one. Store ids as integers (`Type.Integer({ minimum: 0, maximum: PIECE_COUNT - 1 })`) and work out what never changes from the id (LYNGK: `pieceColor(id)`, stacks as `number[]`); store `{ id, playerId, kind }` only when the id cannot tell (TZAAR's random start). Ids in entry order can come from the board (`nextPieceId()` = `pieces.length`, PÜNCT) rather than a counter in State.
- An Action's `metadata` is the only record history, the waiting view and the banner get. Record every fact they will show, including what a system effect took: claimed rings with their marbles, removed pieces with owner and kind, whether a jump chain continues. Missing metadata later means rewriting history code against patches, which the coding policy forbids. Once pieces carry ids, the animator reads the boards by id (`animation-lessons.md`), so keep only what text reads: TZAAR's captured stacks became `StackSummary { height, kind }` and a `landedOnHeight`, and metadata nothing reads goes.
- Put rule arithmetic on the state and board models, not in handlers: free/removable checks, jumps, rows and their reach, group isolation, win checks.
- Tests, in `src/definition/game.spec.ts`:
  - one test per rule decision from step 1, driving the real `GameEngine.executeCanonicalAction`;
  - a position helper that rewrites the started state (board, pool, captures) so each rule is tested in a few pieces;
  - **random playouts**: a legal-action generator for every machine state, a seeded chooser, 10–15 games per variant, asserting a single result within a step cap. They catch deadlocks and invalid states no hand-written test reaches.
- **State holds only what play changes** (`docs/DESIGN.md`, *State shape*). Board geometry is rule data: keep the spots in code and store only the pieces on them, keyed by coordinates; GIPF stored all 37 spots, empty ones included, and failed the review. Track turns through the turn manager rather than a field of your own (GIPF's `moverId` repeated the current turn and was never cleared). Nor is State:
  - anything the board can give: PÜNCT's reserves are the set less the player's pieces on the board (`reserveCount()`), its next id `pieces.length`;
  - config that only setup reads: DVONN and TZAAR copied `version` into State and nothing read it;
  - a count of a list also stored: keep `removedRingIds` and make `ringsRemoved` a getter on the hydrated state (YINSH).
- **Keep only each player's latest turn**: `turnManager.seriesKeeps = 'latest'` in the initializer, when the title reads only the current turn and the counts, chosen before any game is stored. A playout test asserts it and that `series.length` stays at two or three (`games/gipf/src/definition/initializer.ts`).
- **A sparse board checks geometry itself.** With only pieces stored, a lookup off the board returns `undefined` rather than throwing, so fold the geometry into the predicates (YINSH `isVacant` = `isPoint(coords) && !ring && !marker`) and let methods that change a piece throw when it is missing.
- **Validate everything an action carries before using it.** `AxialCoordinates` is `Type.Number()` for both fields, so the server accepts any number. `coordinatesToNumber` folds a fractional coordinate onto a real space's key: the PR bot found a TZAAR capture from `{q: 0.5, r: 1}` passing every check between spaces not in line (P1), and a DVONN placement at `{q: -0.5, r: 0}` filling the centre. YINSH's `findRow` built every point between two submitted ends before checking them, so one request could ask for a billion points. Make the board-membership test (`isSpace`, `isPoint`) require `Number.isInteger` for each field, check ends and lengths before building anything from them, and add a regression test with fractional and far-off coordinates. TZAAR and DVONN on `main` still accept fractions (2026-11-16).
- **Put invariants in the schema**: `Type.Array(Piece, { minItems: 1 })` for an occupied stack, integer ranges for ids, `maxItems` where the rules cap a list, `minimum: 1` for a height that cannot be 0. Specs then `assert(<Title>GameStateValidator.Check(state))` on assigned setups and finished games.
- **No compatibility code for a title never deployed.** A field made optional for "games from before" a change (MATRX's disc ids) guards stored games that do not exist; make it required and drop the fallbacks.
- **Probe a branch you cannot reason your way into.** MATRX's "take your own rows at the start of a turn" never ran, because both players' rows are taken after every move. A `throw` in the branch under the playouts showed it; delete what never fires, and record the reading it implied.
- **One rule, one helper.** A rule both packages need (a GIPF-piece counts as two; a stack of potentials is two discs) goes in one exported function, used everywhere, including scripts and specs. So do rule queries the UI needs: LYNGK's UI had its own shortest route and link finder, and its end panel worked out the ranking decider again; they became `HydratedLyngkBoard.shortestPath()`, `lyngkConnections()` and `HydratedLyngkGameState.deciderIndex()`.
- **Legal moves come from one generator.** PÜNCT's `canMove` repeated the filter in `movesOf`. Write a private `*movesFrom(piece)` that yields each move; `movesOf` spreads it and `hasMove` is `!movesFrom(piece).next().done`, which stops at the first.
- **Assert what the flow guarantees** (coding policy #19): a turn that must exist, a spot a push line must reach. `assertExists` rather than `?? []` or an `if` that silently skips.
- **Tournament setup and scores.** Declare `hasScores: false` in the info metadata of a game won or lost without points. `finalScores` reports the value the terminal handler ranks by: for a game won or lost without points, 1 for the winner and 0 for the loser (Oath, Napoleon's Triumph), never captures or another tiebreak. Add `src/definition/competition.spec.ts` beside the game spec, with the playout helpers both share in `src/definition/tests/playthrough.ts` (as `games/estates` does): for every option that changes setup, seat one moves first (and plays White where White begins), an assigned setup differs from the seeded one only in who sits where, and a finished assigned game passes `validateGameResult` with the expected scores.
- **Record every rule reading** in `games/<slug>/docs/rules-interpretations.md`, with the rules' sources, as each is settled, and give each a test. A reading left only in a session's notes fails the review.
- **Work out a turn's outcome once, in the state handler, and record it.** Record a pass in the metadata of the action after which it happens (`passedPlayerId`, on a move and on the last placement when White cannot make the first move), so history and the banner say who passed without replaying the rules or guessing from two moves in a row (YINSH and LYNGK guessed). Work it out in the handler's `onAction`, never in the action's `apply` as well: actions do not import the handler layer, and DVONN and PÜNCT worked the next turn out twice. A turn-flow helper returns `{ next: MachineState; passedPlayerId?: string }`; LYNGK and YINSH call `turnManager.startNextTurn(actionCount, canMove)` and record a pass when the turn holder is still the mover. One `turnHolder(state)` asserts that a turn exists, and every handler's `enter` sets `activePlayerIds = [turnHolder(state)]`. Clear flow fields when the game ends (YINSH's `resolvingPlayerIds`), and test it.
- **Tests the review expects** (DVONN `competition.spec.ts`, LYNGK `game.spec.ts`):
  - a fixed `MASTER_SEED` in `tests/playthrough.ts`, passed to `engine.startGame(game, { masterSeed, startingPositions })`, and a test that the same seed deals and plays the same game;
  - a pass recorded when the opponent cannot move and not when they can, read from `processedActions[0].metadata`;
  - Random colour really random: over seeds 1–8 both players get White; the same for Creator and Opponent when the owner is not seated;
  - the competition spec sets the game's owner so Creator and Opponent each name a different player than seat one, and runs every version × colour choice;
  - `finalScores` asserted in the win and draw tests themselves;
  - a constructed position for each reading the playouts practically never reach (YINSH: neither player can move);
  - once a helper is made private, test it through the public query (`destinationsFrom(...)` is `[]`).
- **A limit you recommend is yours, not the rules'.** GIPF with Potentials capped the potentials at 12 per player, a recommendation the user took, then asked whether the rules said so; they did not, and the cap went. When offering a limit the rules leave open, say it is yours and quote the rules' own numbers beside it.
- **Describe each choice of a list option** (versions, rule sets): give every choice its own `description`, which the game form shows under the selector for the choice made, and keep the option's `description` as the combined text older site forms show (Fresh Fish; GIPF `7331cd845`). Without it the form runs every choice's explanation together in one paragraph.
- **Options that depend on other options** (GIPF with Potentials: Ultimate fixes every potential count at 3). Upstream's game form now shows each list menu's stored value and each choice's own description, so explain a choice's consequences in its description. Only greying out an option needs more: the fork branch `game-form-option-state` (off upstream `main`, kept to that one change so it stays an easy PR) adds an optional `GameConfigurator.isOptionDisabled(config, optionId)`, which the form honours on every kind of control. Base the title's branch on it, with the user's agreement; the configurator sets dependent values in `updateConfig` and disables them through `isOptionDisabled`.
- **Who plays which colour** at game creation: a config list (Random / Game creator / Opponent) turned into a `StartingPositionAssignment` by a private `chosenWhite(game)` in the initializer, used as `assignment ?? this.chosenWhite(game)`, so an assigned starting position (tournaments) wins. The creator is the player whose `userId` is the game's `ownerId`; a creator who is not seated leaves White to the draw; in a local game every seat has the owner's id, so the first listed seat counts as the creator's. Offer it on every title whose colours decide who starts: the maintainer added it to GIPF and YINSH after their merge, after a player asked (`dc33c3d3e`, `891013da4`).
- **Config readers default only a missing value; an unknown one throws.** `if (config.version === undefined) return Version.Standard`, then `find` the value among the known ones and ``assertExists(found, `Unknown version ${String(config.version)}`)``. Test each reader: missing gives the default, known reads, unknown throws. Add `normalizeConfig` (with `Value.Check`) only where a setting is derived from another (GIPF with Potentials' Ultimate stores every count as 3, `4497039ac`).
- Keep a title's choices that are not rules (default light board, show coordinates, ripple water) in a `TitlePreferenceDefinition`, not in Game config. Adding a key with a default needs no version bump; a saved explicit choice still overrides the new default, which looks like a bug to the user ("the default should be light") until they toggle once.
- **Removing or renaming a preference key** in a deployed title needs a version bump and a `migrations` entry from each older version (`migrations: { 1: () => ({}) }` when nothing carries over); without it, everyone with a saved choice gets a "Preference migration is unavailable" popup. Test it with `resolvePreferences` on a record of the old version. Dropping the whole definition needs no migration, and nor does a title not yet deployed: the review removed LYNGK's version-1 migration before its merge.
- **Pieces that cover several spaces** (PÜNCT): store each as its anchor space, its rotation (0–5) and the level it rests on, and derive its spaces from its kind; keep the board as a list of pieces, with a cache of what lies over each space kept outside the saved state (a `WeakMap` keyed by the hydrated board, cleared on every change), or rule checks redo the work for every candidate move. Generating every move of 30 pieces then took 4 ms.
- **Keep which way a piece lies, even when the rules cannot tell.** PÜNCT's straight piece with its PÜNCT in the middle covers the same spaces half a turn round, so the rules have three rotations for it, but its flecks show which way it lies. Stored as 0–2, a turn that ended half a turn round snapped its flecks round as it settled. Store the true orientation (0–5) and compare with a rule-level `sameOrientation` (turning it half round in place is no move); the user preferred this to mirroring the flecks so both ways looked alike.
- **A board option** (MATRX: its own 40-spot board, or GIPF's 37): keep the shape in game state and build one geometry object per shape (points, spots, dots, entries, lines) that the board model, the UI's view and the notation all read. Derive spots and dots from the points (a spot has all six neighbours on the board), so a new shape is one list of points.
