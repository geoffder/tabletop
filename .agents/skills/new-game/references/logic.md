# Logic

- Model a move the player makes in several clicks as several Actions with machine states between them (place, then remove; each jump of a chain; push, then take a row). Undo then steps back one click at a time, and history can group them.
- An Action's `metadata` is the only record history, the waiting view and animation get. Record every fact they will show or animate, including what a system effect took: claimed rings with their marbles, removed pieces with owner and kind, the line a push moved and how many pieces shifted, whether a jump chain continues. Missing metadata later means rewriting history code against patches, which the coding policy forbids.
- Put rule arithmetic on the state and board models, not in handlers: free/removable checks, jumps, rows and their reach, group isolation, win checks.
- Tests, in `src/definition/game.spec.ts`:
  - one test per rule decision from step 1, driving the real `GameEngine.executeCanonicalAction`;
  - a position helper that rewrites the started state (board, pool, captures) so each rule is tested in a few pieces;
  - **random playouts**: a legal-action generator for every machine state, a seeded chooser, 10–15 games per variant, asserting a single result within a step cap. They catch deadlocks and invalid states no hand-written test reaches.
- **State holds only what play changes** (`docs/DESIGN.md`, *State shape*). Board geometry is rule data: keep the spots in code and store only the pieces on them, keyed by coordinates; GIPF stored all 37 spots, empty ones included, and failed the review. Track turns through the turn manager rather than a field of your own (GIPF's `moverId` repeated the current turn and was never cleared).
- **Assert what the flow guarantees** (coding policy #19): a turn that must exist, a spot a push line must reach. `assertExists` rather than `?? []` or an `if` that silently skips.
- **Tournament setup and scores.** `finalScores` reports the value the terminal handler ranks by: for a game won or lost without points, 1 for the winner and 0 for the loser (Oath, Napoleon's Triumph), never captures or another tiebreak. Add `src/definition/competition.spec.ts` beside the game spec, with the playout helpers both share in `src/definition/tests/playthrough.ts` (as `games/estates` does): for every option that changes setup, seat one moves first (and plays White where White begins), an assigned setup differs from the seeded one only in who sits where, and a finished assigned game passes `validateGameResult` with the expected scores.
- **Record every rule reading** in `games/<slug>/docs/rules-interpretations.md`, with the rules' sources, as each is settled, and give each a test. A reading left only in a session's notes fails the review.
- Record a pass in the metadata of the action after which it happens (DVONN `passedPlayerId`, on the move and on the last placement when White cannot make the first move), so history and the banner can say who passed without replaying the rules.
- **A limit you recommend is yours, not the rules'.** GIPF with Potentials capped the potentials at 12 per player, a recommendation the user took, then asked whether the rules said so; they did not, and the cap went. When offering a limit the rules leave open, say it is yours and quote the rules' own numbers beside it.
- **Describe each choice of a list option** (versions, rule sets): give every choice its own `description`, which the game form shows under the selector for the choice made, and keep the option's `description` as the combined text older site forms show (Fresh Fish; GIPF `7331cd845`). Without it the form runs every choice's explanation together in one paragraph.
- **Options that depend on other options** (GIPF with Potentials: Ultimate fixes every potential count at 3). The shared game form draws every option from one fixed list, shows list options' descriptions nowhere, and, on `main`, shows each list menu's default whatever is stored. The fork branch `game-form-option-state` (off `main`) adds `GameConfigurator.optionState(config, optionId)` returning `{ disabled?, note? }`, a note shown under the menu, and makes list menus show the stored value; base the title's branch on it, with the user's agreement, so the upstream change stays a PR of its own. The title's configurator then sets dependent values in `updateConfig` and greys them out through `optionState`.
- **Who plays which colour** at game creation: a config list (Random / Game creator / Opponent) turned into a `StartingPositionAssignment` in the initializer; an assigned starting position (tournaments) wins. The creator is the player whose `userId` is the game's `ownerId`; in a local game every seat has the owner's id, so the first listed seat counts as the creator's.
- Keep a title's choices that are not rules (default light board, show coordinates, ripple water) in a `TitlePreferenceDefinition`, not in Game config. Adding a key with a default needs no version bump; a saved explicit choice still overrides the new default, which looks like a bug to the user ("the default should be light") until they toggle once.
- **Removing or renaming a preference key** needs a version bump and a `migrations` entry from each older version (`migrations: { 1: () => ({}) }` when nothing carries over); without it, everyone with a saved choice gets a "Preference migration is unavailable" popup. Test it with `resolvePreferences` on a record of the old version. Dropping the whole definition needs no migration.
- **Pieces that cover several spaces** (PÜNCT): store each as its anchor space, its rotation (0–5) and the level it rests on, and derive its spaces from its kind; keep the board as a list of pieces, with a cache of what lies over each space kept outside the saved state (a `WeakMap` keyed by the hydrated board, cleared on every change), or rule checks redo the work for every candidate move. Generating every move of 30 pieces then took 4 ms.
- **Keep which way a piece lies, even when the rules cannot tell.** PÜNCT's straight piece with its PÜNCT in the middle covers the same spaces half a turn round, so the rules have three rotations for it, but its flecks show which way it lies. Stored as 0–2, a turn that ended half a turn round snapped its flecks round as it settled. Store the true orientation (0–5) and compare with a rule-level `sameOrientation` (turning it half round in place is no move); the user preferred this to mirroring the flecks so both ways looked alike.
- **A board option** (MATRX: its own 40-spot board, or GIPF's 37): keep the shape in game state and build one geometry object per shape (points, spots, dots, entries, lines) that the board model, the UI's view and the notation all read. Derive spots and dots from the points (a spot has all six neighbours on the board), so a new shape is one list of points.
